# Finding correlation

Scanner persistence now uses `services/correlation.py` to identify canonical issues and scanner observations. CLI, API, synchronous, queued and scheduled scans share this behavior through the existing runner.

For secret matches with a SHA-256 digest of the complete detected value, issue identity includes organization and repository IDs plus that digest. Scanner names, rule names, line numbers and paths do not split the same credential within one repository. Unassociated local scans remain scoped to the absolute file path. Different repositories and organizations remain separate.

Custom patterns, Git history patterns, Gitleaks, TruffleHog, complete YARA credential matches and appropriately configured heuristic rules supply value digests. Custom YARA rules must opt in with `secret_value = true` only for complete credential strings. Private-key headers alone do not identify a complete key and do not receive a secret digest. Detect-secrets supplies an opaque observation digest for same-tool matching; its detector hashes are not assumed equivalent to plaintext SHA-256. Other matches retain scanner, detector, category, path and location identity. An observation digest permits line movement; without one, moving a match can create a separate finding. No title/category-only cross-tool matching is performed.

Evidence identifies the scanner, detector, path, commit/ref and history change type. Repeated scans update its latest location and timestamp rather than append duplicate rows; metadata retains the first/latest job IDs and an observation count. Renamed files produce a new evidence location attached to the same digest-based repository finding. Detector metadata, title, severity and confidence are retained on evidence and exposed in finding-detail API responses. The canonical finding keeps the first title/source, strongest observed severity/confidence/risk, existing operator ownership/notes and triage behavior. Source-tool filters still refer to the canonical primary source; inspect evidence for all contributing scanners. Scan result counts continue to mean detector matches, not newly created unique issues.

Upgrade with the existing `orgscan init-db` migration workflow. Alembic revision `20260911_0006` adds nullable unique evidence fingerprints and JSON provenance. The migration preserves existing findings/evidence and does not try to reconstruct unavailable secret values or merge historical hashes. The first rescan after upgrade can therefore create new canonical records alongside legacy records. Hashes are sensitive derived data and should remain under the same access controls as findings.

Limits: this is conservative exact-value correlation, not semantic credential equivalence or automatic rename detection without a value digest. A repeated observation stores its latest location, not a full per-scan location history. Existing repository locking serializes managed repository scans; arbitrary concurrent writers can still encounter database uniqueness errors and must retry their transaction. Third-party scanner metadata must follow the redaction contract. Migration tests exercise fresh and populated prior SQLite schemas; PostgreSQL and live external scanners are not certified by these tests.
